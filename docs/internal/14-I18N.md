# 14 · Internationalization (EN / VI)

## 1. Stack

Paraglide JS 2 (inlang). Messages compiled to tree-shakable functions —
only used keys ship, per-locale chunks. Source of truth:
`messages/{en,vi}.json`. Locale = app setting (`tp.settings.locale`),
**not** URL-based (this is an app, not a content site); initial default from
`navigator.language` (vi* → vi, else en).

### Project config and strategy

Added 2026-08-19 — this section previously stopped at "source of truth:
`messages/{en,vi}.json`", which is not enough to configure the compiler
(doc 22 §Exit review, item 2).

`project.inlang/settings.json` declares `baseLocale: "vi"`, `locales:
["vi","en"]`, and the message-format plugin with `pathPattern:
"./messages/{locale}.json"` so the documented file layout is what actually
ships.

**The inlang plugins are resolved from `node_modules`, not from a CDN.** Every
inlang example points `modules` at jsdelivr URLs, and the SDK caches the fetched
files under `project.inlang/cache/`. That cache cannot be committed — the SDK
writes its own `project.inlang/.gitignore` excluding everything except
`settings.json` — which would leave `pnpm build` depending on a third-party CDN
being reachable. Since a push to `main` *is* the deploy, that is a CDN outage
standing between a commit and production. Installing
`@inlang/plugin-message-format` and `@inlang/plugin-m-function-matcher` as
devDependencies and pointing `modules` at
`./node_modules/…/dist/index.js` removes the fetch entirely: no cache directory
is created, and the build is reproducible offline.

(Written on 2026-08-19 as "commit the cache"; corrected the same day on finding
the SDK's own gitignore makes that impossible.)

The compiler runs as a Vite plugin, ordered **before** `sveltekit()`, emitting
to `src/lib/paraglide` with `emitTsDeclarations: true`. The declarations are the
lever that keeps `pnpm lint` green: `svelte-check` reads the `.d.ts` and never
type-checks generated `.js` under `checkJs: true`, which would otherwise be a
third instance of the lint-runs-before-build ordering trap already recorded in
CLAUDE.md. Generated output is gitignored, and told to prettier, eslint and knip
explicitly.

**Strategy: `['custom-tpsettings', 'preferredLanguage', 'baseLocale']`.**
Paraglide's built-in `localStorage` strategy is deliberately **not** used — it
keeps the locale under its own key (`PARAGLIDE_LOCALE` by default), which would
be a fourth localStorage key and is forbidden by doc 05 §2. The custom client
strategy reads and writes `tp.settings.v1.locale` through the settings store
instead. `url` is not used at all, per this section's own rule.

The strategy is defined in `hooks.client.ts`'s `init`, which SvelteKit awaits
before hydration — that ordering is the guarantee that no `m.*()` call can run
before the strategy exists.

**A rune-backed custom strategy must not write synchronously.** The first time
`getLocale()` resolves, Paraglide writes the result back through every strategy
that has a `setLocale` — `setLocale(resolved, { reload: false })`, guarded by a
`localeInitiallySet` flag in the generated runtime. That first resolution
happens inside a component render in practice, because the first thing that
asks for the locale is a message in some template, and mutating `$state` during
render is `state_unsafe_mutation` — which takes down the whole component tree,
not just the widget. Found 2026-08-19 when the deck rendered exactly one tile
out of six.

Three layers, because one is not enough to trust: `settings.patch()` ignores a
patch that changes nothing (which this write-back always is, since the value it
resolved came from the store); the strategy defers a genuine change with
`queueMicrotask`; and `installLocaleStrategy()` calls `getLocale()` once itself,
so the flag flips outside any render.

`setLocale()` keeps its default `reload: true`. The prerendered shell,
`<html lang>`, and `static/boot.js` all have to agree on the locale, and
`reload: false` would require remounting the app root, which tears down and
rebuilds the entire gridstack deck. A reload re-runs `boot.js`, so everything
agrees by construction.

## 2. Key conventions

- Dot-namespaced: `widget.weather.title`, `widget.weather.empty.action`,
  `common.retry`, `settings.theme.dark`, `legal.gate.accept`.
- Every widget owns `widget.<id>.*`; shared strings only under `common.*`.
  A documented static page owns its own namespace — `legal.*`, `settings.*`,
  `about.*` — because its prose is not shared with anything and burying it
  under `common.*` would make that namespace the junk drawer.
- No string concatenation for sentences — always parameterized messages
  (`m['widget.weather.stale_age']({ minutes })`), because VI/EN word order
  differs.
- **Call sites use bracket access.** A dot-namespaced key compiles to an
  arbitrary module export name — Paraglide emits
  `export { legal_gate_accept as "legal.gate.accept" }` — so the key survives
  into the call site verbatim and `m['legal.gate.accept']()` is the form.
  (Corrected 2026-08-19: this section previously showed `m.stale_age(…)`, a
  dotless key, which contradicted the dot-namespacing rule two lines above it.
  Dotted keys and property access cannot both be had.)
- Plurals: VI has no plural inflection; still use ICU-ish params so EN gets
  `1 item / 2 items` correctly (Paraglide variants).
- **Hardcoded-string ban:** ESLint rule (`no-restricted-syntax` on JSX-ish
  text nodes is not applicable in Svelte — use `eslint-plugin-svelte`'s
  text-content heuristics + a repo script `pnpm i18n:audit` that flags
  Vietnamese/English words in `.svelte` markup outside `m.*()` calls).
  CI-blocking from Week 2 — turned on 2026-08-27 with a backlog of zero, so
  there was nothing to phase in.

## 3. Formatting (never hand-roll)

- Dates/times: `Intl.DateTimeFormat(locale)` via `lib/i18n/fmt.ts` helpers
  (`fmtTime`, `fmtDate`, `fmtRelative` using `Intl.RelativeTimeFormat`).
- Numbers/currency/percent: `Intl.NumberFormat`; currency display uses
  `currencyDisplay:'narrowSymbol'`; VND 0 decimals (doc 08 §2).
- Week start: settings override; default vi=Mon, en=locale data.
- Lunar dates: `lib/lunar/format.ts` — `08/07 Bính Ngọ` (vi),
  `7th day, 7th lunar month` (en, spelled out); Can-Chi rendered only in vi
  by default with a toggle in calendar settings.

## 4. Translation workflow

Solo-dev friendly: edit both JSON files in the same PR; CI check
`pnpm i18n:check` fails on key-set drift between en/vi (missing/extra).
Machine-translation placeholders forbidden — untranslated = key missing =
red CI, so nothing half-translated ever ships.

**`pnpm i18n:check` contract** (`scripts/i18n-check.mjs`, added Week 1). Scope:
`messages/en.json` and `messages/vi.json` only. Exit 0 clean, exit 1 on any
finding, one line per finding, `::error::` annotated on CI. It checks four
things:

1. key-set symmetry, reported in both directions;
2. empty or whitespace-only values;
3. **placeholder parity** — the set of `{name}` tokens must be identical per key
   across locales. This is the check that actually catches a broken VI string,
   as opposed to a missing one;
4. keys that are not dot-namespaced, or that sit outside `common.*`,
   `widget.<id>.*`, `settings.*`, `legal.*`, `about.*`, `error.*`; plus the
   doc 06 §1 rule that every manifest has `<i18nKey>.title` and
   `<i18nKey>.blurb`.

**Check 4's manifest half never ran until 2026-08-27.** It grepped
`registry.ts` for `i18nKey: 'widget.x'`, but manifests live one per folder and
`registry.ts` carries only the *type*, written with backticks — so the pattern
matched nothing and reported clean, for the whole of Week 1. It now globs
`src/lib/widgets/*/manifest.ts`, and a manifest with no `i18nKey` at all is
itself a finding. Found on the day four more manifests were about to land
behind it.

CI-blocking from Week 1 — it is deterministic, sub-second, and has no false
positives.

**`pnpm i18n:audit` contract** (`scripts/i18n-audit.mjs`, added Week 1). Scope:
`src/**/*.svelte`, excluding `src/routes/spike/**` and the generated Paraglide
output. It parses with `svelte/compiler`'s `parse()` and walks the template AST
rather than grepping — `svelte` is already a dependency, and the false-positive
rate of a regex over Svelte markup is exactly what would get a script like this
switched off. It flags text nodes containing letters, and literal
`aria-label` / `title` / `placeholder` / `alt` values, when they are not the
result of an `m.*()` call. Allowlisted: pure punctuation, symbols and digits
(`×`, `·`, `—`), and an explicit `<!-- i18n-audit-ignore -->` escape, which is
what the §6 dual-render blocks use.

Per §2 it was **report-only in Week 1 and is CI-blocking from Week 2**.
Landing the script early kept the backlog visible and shrinking rather than
discovered in one lump; it reached zero before the gate closed.

The mechanism is the flag's default rather than the `--strict` this section
first proposed: from Week 2 the script exits non-zero unless given
`--report-only`. That is the same polarity `tokens-audit.mjs` uses (doc 20 §1),
and one convention across both gates beats two scripts whose flags are each
other's opposite — a gate whose polarity has to be remembered is a gate that
gets invoked wrong. (Changed 2026-08-27.)

**Neither audit ran in CI at all before that date.** `ci.yml` ran `pnpm lint`,
`knip`, tests, build and budgets; `i18n:check` existed only inside `pnpm
verify`, which is a local convenience and not a gate. So the "CI-blocking from
Week 1" claim above was false for the whole of Week 1. All three now have their
own step in `ci.yml`.

## 5. Voice per locale

Same register both languages (doc 12 §8): calm, terse, lowercase-leaning.
VI: neutral friendly, no "bạn ơi", tech terms kept EN where universal
(widget, cache) but everyday actions localized (thêm, xong, thử lại).
EN: no exclamation marks, no cutesy.

## 6. Locale-sensitive edge list (test targets)

- Lunar strings in clock/calendar/quote footers switch correctly.
- `fmtRelative` boundaries (59 s → "1 phút trước").
- Mono numerals unaffected by locale (digits always Latin).
- RSS content is **not** translated — displayed as-is with `lang` attr
  unset (it's third-party content).
- Legal pages exist in both languages; gate shows locale-appropriate text
  with a language switch on the gate itself (doc 16 §2).

### Bilingual prerendering

Added 2026-08-19. `/`, `/legal/*` and `/about` are prerendered to one HTML file
each (doc 03), and the locale lives in localStorage with no URL segment — so the
HTML cannot be locale-specific. Nothing in the suite said how those two facts
coexist, while doc 16 §2 requires the gate to render correctly *before* any
JavaScript runs.

The resolution is to render **both** languages into the pre-JS surfaces and let
CSS pick:

```svelte
{#each LOCALES as l}<div data-locale={l}>{m.legal_gate_body(undefined, { locale: l })}</div>{/each}
```
```css
html[lang='vi'] [data-locale]:not([data-locale='vi']),
html[lang='en'] [data-locale]:not([data-locale='en']) { display: none }
```

Paraglide 2 message functions take `{ locale }` as their second argument, so
both renders come out of the same catalogue and `pnpm i18n:check` covers them —
these are real messages, not hand-written duplicate prose. `static/boot.js`
already sets `<html lang>` before first paint, so the correct one is visible
pre-JS, pre-hydration, and with JavaScript disabled entirely.

The rule is **prerendered prose dual-renders; reactive surfaces call `m.*()`
once**. In practice that is the gate panel, `/legal/*`, `/about`, and
`/offline` — the last one because it is precached and shown exactly when the
network is least willing to help, so it should not depend on hydration to be
legible. Everything else uses plain `m.*()`: the deck renders nothing until it
has mounted and read client storage, and the top bar (doc 13 §1) is icon-only,
so the prerendered chrome carries no translatable visible text that could flash.

(Stated as a list of three surfaces when first written on 2026-08-19; corrected
to the rule the same day, on noticing `/offline` has exactly the same shape.)

The gate's language switch is a pair of links, `/?lang=vi` and `/?lang=en`,
applied by `boot.js` before paint and persisted by the settings store on
hydration. Links rather than a button because a `<button onclick>` does nothing
until hydration, and on a consent screen the first click has to count. This
does not make the locale URL-based: it is a one-shot setter, not routing, and
nothing reads it after the write.

**"Before hydration", not "without JavaScript".** `boot.js` is itself a script;
with JavaScript disabled entirely it does not run, `<html lang>` keeps the `vi`
that `app.html` declares, and `?lang=` has no effect — measured, not assumed
(`e2e/journey-1-first-run.e2e.ts`). What the link pair actually buys is the gap
between first paint and hydration, which on this app is long enough to matter:
`boot.js` blocks in `<head>` while the app bundle does not. A visitor with
JavaScript off sees the gate, can read every linked page, and cannot accept —
the accept button is `disabled` until `browser` is true, which is the honest
state for an app that needs JavaScript to do anything at all.

(Overstated as "works with JavaScript off entirely" when first written on
2026-08-19; corrected the same day after the journey #1 spec measured it.)

**Tradeoff, stated plainly:** those three pages carry both languages in their
HTML, roughly doubling their (small, gzip-friendly) text, and search engines see
duplicate-language content on the legal pages. Against that, it is the only
mechanism that satisfies "gate correct pre-JS", "locale not in the URL", and
"legal pages in both languages" *simultaneously*, without doubling the
prerendered route set or introducing a `[[locale]]` param that §1 forbids. For a
personal dashboard whose legal pages are not an SEO asset, that is the right
side of the trade.
